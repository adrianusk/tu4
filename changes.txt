tu4-1.0 Changes
================

2026-09-20: Fix intro beasties (ANIMATE) vanishing after a Scale change
-----------------------------------------------------------------------
Fixed a bug where changing Scale (or fullscreen) in the Configure menu's
Video settings made the intro beasties / ANIMATE stop drawing.

Root cause:
- A scale/fullscreen change called screenReInit(), the heavy path meant
  for a TEXT-STYLE change. screenReInit() does "delete tu4.imageMgr; new
  ImageMgr" (plus Tileset::unloadImages/loadImages, tile-anim and dungeon
  view teardown), which frees every ImageInfo.
- The intro caches a raw ImageInfo* (beastiesImg = imageMgr->get(
  BKGD_ANIMATE), set in IntroController::init()). After screenReInit()
  freed the old ImageMgr, that cached pointer dangled, so the beasties
  no longer drew. The text-style path recovers by re-running init()
  afterward; the scale path did not (and should not need to).
- A scale change only alters the on-screen window size. The logical
  framebuffer, the loaded ImageMgr/ImageInfo pixels, tiles, tile-anims
  and dungeon-view caches are all unchanged (the text style is the same),
  so reloading them is both wasted work and the cause of the dangling
  pointer.

Fix:
- Added screenResize() (src/screen.{h,cpp}): the window-resize-only path.
  It calls screenInit_sys(reset=1) and nothing else -- no ImageMgr delete,
  no Tileset reload, no tile-anim/dungeon-view teardown. The renderer keeps
  its logical size + nearest scaling, so the same framebuffer is simply
  scaled to the new window.
- IntroController::updateVideoMenu() (src/intro.cpp) now calls
  screenResize() for a scale/fullscreen change instead of screenReInit().
  A text-style change is unchanged: it still defers the full screenReInit()
  + init() reload to the 'c' handler on menu close.

Result: all loaded assets (including the intro's cached beastiesImg) stay
valid across a scale change, so the beasties keep animating; the window
still resizes as before. Verified in-game (user-tested): changing Scale in
the Configure menu resizes the window and the beasties continue to draw.
Header changed, so built with make clean && make; binary copied.

2026-09-12: Fix creature drawn over a door/room face in the 3D dungeon view
---------------------------------------------------------------------------
Fixed a bug where a creature standing on a DOOR (or room) tile two steps
ahead in the first-person dungeon view was drawn on top of / instead of
the door, making the opaque door face vanish and the creature float in
the corridor. Correct behaviour: the door is the nearer, opaque surface,
so it is drawn and the creature on it stays hidden until the party moves
up so the tile is at distance 1 (where the door itself opens to a
distance-0 view).

Root cause:
- getTilesAt() pushes the base dungeon tile LAST, so for a stack
  (tiles.size() > 1) tiles.front() is the topmost overlay (the creature)
  and tiles.back() is the base tile it stands on.
- tilesToGraphic() only looked at tiles.front(). A creature is not
  architecture, so it returned DNGGRAPHIC_BASETILE. In the display loop
  that makes graphicIndex() return -1 (drawWall draws nothing -> the door
  face is skipped) and then drawInDungeon(tiles.front()) draws the
  creature. Result: creature shown, door gone.

Fix (src/dungeonview.cpp tilesToGraphic):
- When a stack sits on a base tile, also inspect the BASE tile
  (tiles.back()). If it is opaque architecture (DUNGEON_WALL /
  SECRET_DOOR -> DNGGRAPHIC_WALL, DUNGEON_ROOM / DOOR -> DNGGRAPHIC_DOOR),
  return that wall/door type. drawWall() then renders the nearer opaque
  face and the loop's drawInDungeon() overlay is SKIPPED (its guard only
  fires for DNGTILE/BASETILE) -- so the creature behind the door is not
  drawn at all ("just draw what is nearer", rather than draw-then-cover).
- A creature on an OPEN corridor/floor base still falls through to
  BASETILE and is drawn normally. A rarer front-tile-is-architecture case
  is handled first.
- Behaviour fix, not a literal xu4 port: xu4's tilesToGraphic has the same
  front-only limitation and likely shares this bug.

Verified in-game: with a door tile two steps ahead, the NPC (tested bat
and rat) is hidden behind the door face and only becomes visible after
moving to distance 1. Built clean (.cpp-only), binary copied.

File changed: src/dungeonview.cpp (tilesToGraphic).

2026-09-12: Fix dungeon crash / black screen after live text-style change
--------------------------------------------------------------------------
Fixed a crash (and, after a first partial fix, a black dungeon) when the
player changes the Text Style while a dungeon game is in progress:
enter a dungeon -> Ctrl-Q back to the main menu -> Configure -> change
textStyle (e.g. EGA -> U5-EGA) -> Journey Onward.

Root cause (two linked bugs):
- The DungeonView (held in the Screen struct, created once by
  screenMakeDungeonView() and guarded by `if (dungeonView) return`)
  caches RAW pointers into the current scheme's images/ASP data:
  dungObj0Data / dungNpc1Data / dungObj1Data (from image->getAspData())
  and the graphic[].info/.sub array. The deferred text-style reload runs
  screenReInit(), which does `delete xu4.imageMgr` + Tileset::unloadImages()
  -- freeing exactly those images. screenReInit() did NOT touch the
  DungeonView, so its cached pointers dangled -> SIGSEGV on the next
  dungeon draw ("Journey Onward").
- A first fix merely NULLed the DungeonView in screenReInit(). That stopped
  the crash but produced a BLACK dungeon: resuming an in-progress dungeon
  via journeyOnward() takes the "return to a running game" path
  (xu4.saveGame set -> StagePlay), which does NOT call setMap() -- the
  location is unchanged -- so screenMakeDungeonView() never re-ran, the
  DungeonView stayed NULL, and the draw path `if (dungeonView)` (screen.cpp)
  simply skipped rendering.

Fix (src/screen.cpp screenReInit()):
- Inspect whether in-progress dungeon graphics state is loaded (a non-NULL
  Screen::dungeonView means a dungeon game is active). Record hadDungeonView,
  delete the stale DungeonView during teardown (its pointers reference
  soon-to-be-freed images), then AFTER the rebuild (`new ImageMgr` re-points
  baseSet to the new textStyle; newTileAnims; Tileset::loadImages()) call
  screenMakeDungeonView() again to RECREATE it -- re-caching every image/ASP
  pointer against the new scheme. Recreate (not just NULL) because resume
  does not go through setMap().
- Safe because the recreate happens after imageMgr + tileset are rebuilt,
  and the game context (c) and the config's tileset are still alive while the
  game is in progress. Other views (world/city/combat) look images up on
  demand each frame and refresh automatically, so only the pointer-caching
  DungeonView needed this hook.

Built clean (incremental, .cpp-only change) and binary copied.

File changed: src/screen.cpp (screenReInit).

2026-09-12: EGA theme separate N/S dungeon wall art (per-heading blue/green)
----------------------------------------------------------------------------
Gave the "EGA" text style distinct east-west vs north-south dungeon
wall/door art so the 3D first-person view matches xu4's EGA look, where
a wall's colour tracks its WORLD orientation, not the player's facing.
Previously tu4's EGA theme pointed both orientations at one ASP file, so
the whole corridor was a single colour that just followed player heading
(all blue or all green). This is the roadmap FUTURE item "North/South
dungeon wall variant"; we took the "separate ns ASP files" route (tu4's
fixupDungNS is a no-op stub — a per-pixel RGB swap has no text-mode
equivalent, and recolouring char+attr art at load time is awkward).

How xu4 does it (verified in /home/adrianus/xu4-1.0):
- dungeonview.cpp graphicIndex() selects one dngGraphicInfo entry per
  wall piece: index = doorBase + (xoffset+1)*2 + distance*6, then +1 when
  orientation is NORTH|SOUTH. Each distance block is
  {lft_ew, lft_ns, mid_ew, mid_ns, rgt_ew, rgt_ns}, so the SAME
  orientation bit picks the _ns variant for BOTH the side walls (lft/rgt)
  and the facing wall (mid).
- The colour difference between side and facing walls comes from the
  SOURCE FILES, not the code: EGA graphics.xml feeds lft/rgt from
  dungeonhall.png (base BLUE) and mid from dung0ma.png (base GREEN); the
  _ns entries add fixup="dungns", an all-image blue<->green swap
  (imagemgr.cpp fixupDungNS). Net per view:
    facing E/W -> side walls BLUE, wall ahead GREEN
    facing N/S -> side walls GREEN, wall ahead BLUE
  i.e. side vs facing are always opposite colours, and both flip when you
  turn 90 degrees. (CGA/compcga/PC9801 ship explicit *_ns.png files with
  no fixup, where dung0ma_ns is the inverse colour of dung0ma — the
  pre-coloured-file model tu4 now follows.)

Asset pipeline (graphics/ega/imgsrc44 -> graphics/EGA):
- 39 source PNGs (44x44 dungeon art: hall/door walls per distance, plus
  ladders and traps) converted PNG -> .psci (Playscii batch_png2psci.py,
  44x44, charset dos40, palette ega) -> .ASP (psci2asp_44.py, lossless
  char+attr copy). Both are batch tools; every .ASP is 3879 bytes
  (7-byte BSAVE header fd/segB800/off2040/len3872 + 44*44 char+attr).
- Playscii discards PNG alpha (Image.convert('RGB')): fully-transparent
  pixels flatten to black and encode as char 0 / attr 0x00 (opaque black
  rectangle), NOT transparency. New post-process
  graphics/converters/asp_blackfill_to_space.py rewrites exactly the
  char0/attr0 cells to space (0x20), the tu4 transparency marker (space
  char = transparent, any attribute; per 2026-09-07). Narrow rule: a scan
  showed char0/attr0 is the ONLY black-on-black combination present and
  real content uses non-zero chars/attrs, so it cannot punch holes in
  opaque black. 52331 cells rewritten across 31/39 files; the 8 fully
  opaque source PNGs (no alpha) were left untouched.
- Copied all 39 .ASP into graphics/EGA/ (literal copy; adds _ew/_ns
  suffixed dungeon/hall files alongside the legacy un-suffixed names and
  a lowercase traps.ASP next to the existing TRAPS.ASP).

Facing-wall colour correction (name swap):
- The new source art was authored as _ew=BLUE / _ns=GREEN UNIFORMLY. That
  is correct for the SIDE-wall files (dungeonhall_ew=blue, _ns=green ==
  xu4) but INVERTED for the FACING-wall files, which xu4 has as
  dung0ma EW=green / NS=blue. Fixed by swapping the ew<->ns filenames of
  the 5 facing-wall pairs only (dung0ma, dung0ma_door, dung{1,2,3}ma_door)
  via a temp name, so _ew now = green and _ns = blue for those. Side-wall
  files left as-is. Verified post-swap: facing files _ew=green/_ns=blue,
  side files _ew=blue/_ns=green.

Config (conf/graphics-text.xml, EGA imageset ONLY; minimal-diff):
- Halls: dungew->dungeonhall_ew.ASP, dungns->dungeonhall_ns.ASP,
  dungew_door->dungeonhall_door_ew.ASP, dungns_door->..._door_ns.ASP.
- Back walls (xu4 model: distances 1-3 are y-offset crops of the
  distance-0 file, NOT separate files): all dungback* EW subimages now
  crop dung0ma_ew.ASP; added parallel dungback{0,1,2,3}_ns image entries
  cropping dung0ma_ns.ASP. The old per-distance dung1ma/2ma/3ma.ASP are no
  longer referenced by EGA. (Verified the y=8/16/20 crop regions of the
  new dung0ma files carry the same content the old standalone files had.)
- Door mids: dung{0,1,2,3}_mid_ew_door* -> dung{N}ma_door_ew.ASP,
  _ns_door* -> dung{N}ma_door_ns.ASP.
- U5-EGA and PC9801 imagesets UNCHANGED: both orientations still share one
  file (the "theme that doesn't differentiate points to the same
  subimage" case; matches xu4 u5ega which uses fixup on a shared file).
- No code change. dungeonview.cpp already resolves _ew/_ns purely by
  SUBIMAGE NAME via ImageMgr::imageInfo()'s global scan over all image
  entries, so splitting/renaming the parent <image> entries is safe (all
  subimage names preserved). fixupDungNS stays an unused no-op stub.

New tool: graphics/converters/asp_blackfill_to_space.py (batch/single,
--dry-run, --space). Files changed: conf/graphics-text.xml (EGA imageset);
new/updated graphics/EGA/*.ASP dungeon art; roadmap.txt (item resolved for
EGA).

Interior flat-fill cleanup (same day):
- The PNG->.psci glyph match left dither/shade glyphs (0xB0 light, 0xB1
  medium, 0xB2 dark, 0xFA centred dot) scattered inside the solid-colour
  wall interiors, making the flat walls look "dirty". New tool
  graphics/converters/asp_clean_inner_shading.py rewrites such a shading
  cell to the clean fill char 0x00 ONLY when all 8 neighbours are interior
  (flat fill 0x00 or another shading glyph) -- if any neighbour is a
  detail/edge glyph, the transparency marker (0x20), or the image border,
  the cell is kept. This flattens interior noise while preserving the
  diagonal perspective edges and the corridor-opening rim. The ATTRIBUTE
  byte is never touched, so the blue/green flat colour is unchanged.
- Applied to graphics/EGA: 955 interior cells cleaned across the dungeon
  wall/door files (e.g. dungeonhall_ew 89->4 shading glyphs, dung0ma_ew
  ~95->14, the survivors all edge-adjacent). Ladders/traps: 0 (untouched).
  Files stay 3879 bytes. Edges verified intact by grid visualisation.

2026-09-11: Intro EGA assets, per-theme virtue-card placement, and two
                build/config bug fixes
--------------------------------------------------------------------------
Decoded the remaining EGA intro screens to ASP, made the gypsy
character-creation virtue cards positionable per theme via new abacus
art attributes, and fixed two bugs hit along the way (a stale-object
build that broke startup, and a wrong card-draw offset).

Intro EGA assets (graphics/ega/imgsrc/):
- Decoded 11 LZW-compressed EGA intro screens to PNG with u4dec
  (`u4dec lzw <F>.EGA <F>.png 320 200`): PORTAL, TREE, OUTSIDE, WAGON,
  GYPSY, INSIDE, then HONCOM, VALJUS, SPIRHUM, SACHONOR, ABACUS. All are
  filetype image/x-u4lzw at 320x200 depth 4 per the EGA imageset in
  conf/graphics.xml.
- Converted each PNG -> 80x50 .psci (Playscii batch_png2psci.py, charset
  dos40, palette ega) -> 80x50 .ASP (graphics/converters/psci2asp_44.py
  batch mode, --width 80 --height 50). Every .ASP is 8007 bytes (7-byte
  BSAVE header fd/segB800/off2040/len1F40=8000 + char+attr payload).

Per-theme virtue-card placement (drawCard):
- The gypsy question cards are now placed by CHOICE, not by crop origin:
  choice A (pos 0) always draws in the LEFT slot, choice B (pos 1) in the
  RIGHT slot. Slot coordinates come from new leftx/rightx/top attributes
  on the abacus <image> element (view-relative, 0-based). The card's
  pixels still come from its own subimage crop; only the destination
  changed.
- Replaced the old fixed originTable path. drawCard now reads
  BKGD_ABACUS's cardLeftX/cardRightX/cardTop and draws at (slotX, slotY),
  falling back to the card's own crop (subimage x-1, y-1) if the
  attributes are unset (-1).
- New ImageInfo fields cardLeftX/cardRightX/cardTop (imagemgr.h), parsed
  in loadImageInfo() (config_xml.cpp) as leftx/rightx/top, default -1.
- graphics-text.xml: added leftx/rightx/top to all three abacus images,
  each matching that theme's own card crop origin (they differ because
  U5-EGA's abacus is FM-Towns-derived): U5-EGA 6/53/4, PC9801 4/56/4,
  EGA 3/55/3.

Bug fix 1 -- stale-object build broke startup (no window, 100% CPU):
- Adding fields to the ImageInfo struct in imagemgr.h and then doing a
  plain incremental `make` linked object files compiled against two
  different sizeof(ImageInfo) layouts (the Makefile has no header
  dependency tracking). The resulting heap corruption sent
  std::map::operator[] on ImageInfo::subImageIndex into an infinite loop
  inside loadImageInfo(), so the SDL window was never created (nothing in
  the taskbar) and the process spun at 100% CPU.
- Fix: full clean rebuild (`cd src && make clean && make && cp tu4 ..`)
  so every .cpp is compiled against the new struct layout. Rule captured
  in .kiro/steering/tu4-development.md: ANY .h edit requires make clean.
- (Also confirmed a separate red herring: validateXml=1 in
  ~/.config/tu4/tu4rc makes libxml2 DTD validation pathologically slow at
  startup on this system; shipping default is validateXml=0.)

Bug fix 2 -- both cards drew in the top-left corner:
- drawCard first computed dx = slotX - (cardSub->x - 1), but
  ImageView::draw(Symbol, dx, dy) writes each cell at
  (view.x + dx + col) -- dx,dy are the ABSOLUTE view-relative destination
  and the source column is NOT added back. Since slot == crop for a given
  theme, the offset cancelled to 0 and both cards landed at column 0.
- Fix: pass the slot coordinates directly (dx = slotX, dy = slotY); the
  fallback path uses (cardSub->x - 1, cardSub->y - 1).

Files changed: src/imagemgr.h, src/config_xml.cpp, src/intro.cpp,
               conf/graphics-text.xml (abacus leftx/rightx/top x3),
               .kiro/steering/tu4-development.md;
               new graphics/ega/imgsrc/*.{png,psci,ASP} for the 11 intro
               screens. (conf/dtd/graphics.dtd was left unchanged;
               validation is non-fatal and off by default.)


2026-09-07: New "EGA" text style, simplified transparency rule, converter
                cleanup, and MYSHAPES<->SHAPES round-trip tooling
--------------------------------------------------------------------------
Added a third text-mode theme "EGA", relaxed the tile transparency test
to "space character = transparent" (any attribute), normalized which
tiles are opaque vs transparent in the U5-EGA and EGA MYSHAPES.ASP art,
retired the obsolete PNG->ASP converters, and added a reverse
serializer (aspdecode.py) plus a per-tile transparency reference table.

New "EGA" text style (conf/graphics-text.xml):
- Added a complete <imageset name="EGA"> (84 image entries, same
  structure/counts as U5-EGA and PC9801) and a matching
  <tileanimset name="EGA">, all referencing graphics/EGA/ paths.
- EGA uses the classic TITLE.ASP intro-animation subimage coordinates
  and the classic ABACUS.ASP bead layout (ystart=6), matching the files
  present in graphics/EGA/ (not the FM* variants).
- Theme is auto-discovered: schemeNames() (config_xml.cpp) enumerates
  <imageset name>, so "EGA" appears in the Configure -> Text Style menu
  with no recompile. checkAssets() requires only MYSHAPES/START/TITLE
  (all present), so EGA does not fall back to the default. dungeonview
  branches on textStyle ending in "EGA", so EGA uses the EGA dungeon
  scale tables like U5-EGA.
- Seeded graphics/EGA/ with placeholder ASPs copied from U5-EGA for the
  files it lacked, so the theme loads immediately; these are overwritten
  as real EGA art is produced.

Simplified transparency rule (engine): space char = transparent.
- Changed the tile/dungeon/image transparency test from the strict
  marker "char 0x20 AND attr 0x00" to "char == 0x20" (space, ANY
  attribute). A space with a non-zero attribute (e.g. gray-on-black
  0x20/0x07, which the new Playscii-authored art uses everywhere as
  background fill) is now correctly treated as transparent.
- Edited all draw paths: tileanim.cpp (animDrawTile,
  animDrawTileScroll), tileview.cpp (static path), image.cpp (draw,
  drawSubRect), screen.cpp (map-area blit), dungeonview.cpp (all 5
  tile/object skip tests). Left the intro title-fade logic
  (titleCellVisible) untouched -- it is a different concept.
- Consequence for authoring: to make an all-black-rendering space cell
  OPAQUE, convert it to full block 0xDB with fg = the space's ORIGINAL
  BACKGROUND nibble (bg 0). This preserves solid colour (e.g. lava's
  red-background spaces became 0xDB/0x0C, not black).

MYSHAPES.ASP transparency normalization (U5-EGA and EGA):
- The intent is captured in a new reference table (see below). The rule
  divides tiles into opaque (terrain, letters/spacers, fields, lava,
  moongate, waterside, rocks, ankh, dungeon_floor, ruins, shrine) vs
  transparent (avatar/party/NPCs/monsters, ship, horse, balloon, chest,
  corpse, flashes, etc.).
- Opaque tiles that were authored with space fill had those spaces
  converted to full block (fg = original bg nibble). U5-EGA: letters
  96-126, terrain 0-15, dungeon_floor(22), ruins(29), shrine(30),
  waterside(49-52), rocks(55), ankh(61), fields(68-71), lava(76),
  moongate/openings(64-67). EGA: same set.
- Ship (16-19): EDGE space cells are transparent, but the two INTERIOR
  hull cells (frame 0 r2c1, frame 2 r2c2) were made opaque so water does
  not show through the middle of the hull. Applied to both themes.
- sea_serpent: frame 0's lone stray space was replaced with frame 1's
  glyph so both frames are opaque/consistent (the theme art simply has
  no transparency for it; the table INTENT stays YES).
- Known theme-art gaps vs the table (both themes): pirate_ship W/E
  facings (128,130) transparent while table says no; sea_serpent(136-137)
  and slime[1]/[3] (161,163) opaque while table intends YES. These are
  the current art's properties, not the design intent -- 250/256 match.

Transparency reference table (graphics/converters/tile_transparency.md):
- New doc: idx 0-255 -> tile name (frame-annotated) -> transparent
  YES/no, ordered by conf/tilemap-base.xml (Ultima IV save id). This is
  the theme-independent INTENT; rows marked (*) are manual overrides of
  a raw file scan (e.g. letters/spacers -> no; moongate -> no; horse and
  balloon -> yes). Totals: 169 transparent / 87 opaque.

Converter cleanup (graphics/converters/):
- REMOVED the obsolete PNG->ASP glyph-matching converters (png2asp.py,
  png2asp_v2.py, png2asp_dung.py, png2asp_dungnpc2.py, png2asp_scobj.py,
  png2asp_scobj_rgba.py). Authoring is now Playscii (.psci) -> ASP,
  which is a lossless 1:1 char/fg/bg copy (psci2asp.py / psci2asp_44.py).
- The PNG converters glyph-matched against cp437_8x8.bin, a font that
  did NOT match the engine's cp437_8x8.h -- comparison showed only
  ~54% byte overlap even after bit-reversal, and asymmetric glyphs like
  '(' rendered mirrored. That is a different charset, not just a bit
  order difference.
- REGENERATED graphics/converters/cp437_8x8.bin directly from the engine
  font src/../cp437_8x8.h so it is now byte-identical (2048 bytes,
  MSB-first: bit 7 = leftmost pixel). Previews now match the game.
- Updated converters/README.md: documented the removal, the new font
  provenance, the space-only transparency rule, and aspdecode.py.

New reverse serializer (graphics/converters/aspdecode.py):
- Exact inverse of aspencode.py: MYSHAPES.ASP (256 serialized 32-byte
  tiles) -> SHAPES.ASP (80x60 screen, 20x15 tile grid; unused slots
  256-299 left blank). Verified round-trip
  aspencode(aspdecode(x)) == x byte-for-byte.
- Used to keep SHAPES.ASP in sync after editing MYSHAPES, and vice
  versa, for both U5-EGA and EGA.

Assets processed:
- U5-EGA: SHAPES.ASP <-> MYSHAPES.ASP kept in sync through the edits
  above (aspencode/aspdecode round-trips verified).
- EGA: SHAPES.ASP -> MYSHAPES.ASP (aspencode); transparency normalized
  (250/256 vs table); ship interior fixed; SHAPES.ASP regenerated
  (aspdecode). TITLE.psci -> TITLE.ASP (psci2asp.py, lossless 80x50).

Files changed: conf/graphics-text.xml,
               src/tileanim.cpp, src/tileview.cpp, src/image.cpp,
               src/screen.cpp, src/dungeonview.cpp,
               graphics/U5-EGA/{MYSHAPES.ASP,SHAPES.ASP},
               graphics/EGA/{MYSHAPES.ASP,SHAPES.ASP,TITLE.ASP} + seeded
               placeholder ASPs,
               graphics/converters/{cp437_8x8.bin (regenerated),
               aspdecode.py (new), tile_transparency.md (new),
               README.md};
               removed graphics/converters/png2asp*.py (6 scripts).


2026-09-03: Window/taskbar icon + Linux app-launcher entry
-----------------------------------------------------------
Added an application icon (the avatar figure) for both the running SDL
window (taskbar/dock/alt-tab) and the Linux app launcher (application
menu / file manager). On Linux the icon is NOT embedded in the ELF as
on Windows -- the window icon is set at runtime via SDL, and the
launcher icon comes from a .desktop file + icons installed into the
hicolor theme.

Icon art (the avatar / "Adventurer" tile):
- Source is MYSHAPES.ASP tile 31 (the avatar tile's Ultima IV save id;
  confirmed via tilemap-base.xml mapping order, single frame). Each
  MYSHAPES tile is 4x4 chars = 32 bytes; tile N at offset 7 + N*32, so
  the avatar is at offset 999. graphics-text.xml declares the "tiles"
  image as tiles="256", indexed by tile number directly.
- Rendered to 32x32 px (8px/char cell) using the ENGINE's font header
  src/../cp437_8x8.h, which is MSB-first (bit 7 = leftmost pixel).
  GOTCHA: the graphics/ converter scripts load cp437_8x8.bin as
  LSB-first; using that bit order horizontally MIRRORS every glyph and
  produced a wrong render. The .h font must be read MSB-first.
- Background: solid BLACK. (A transparent "clean cutout" variant -- all
  black keyed out -- was tried first but looked worse, so the full
  black background is kept.) The tile's space+0x00 background cells are
  drawn as black.
- Produced graphics/tu4.bmp (24-bit, black background) and
  graphics/tu4.png (opaque, black background) plus 48x48 and 256x256
  PNG scales.

Runtime window icon (src/screen_sdl2.cpp):
- After SDL_CreateWindow, load graphics/tu4.bmp via SDL_LoadBMP (core
  SDL only -- no SDL_image dependency), then SDL_SetWindowIcon. No color
  key (background is opaque black). Fails gracefully (verbose-only
  warning) if the BMP is missing. Path is relative to the working dir
  (where tu4 is launched). Built clean (make, exit 0), binary copied.
  (SDL3 backend screen_sdl3.cpp left unchanged; build config is UI=sdl2.)

App-launcher entry (Linux desktop integration):

2026-08-14: Fix use-after-free crash in moveObjects (world map)
---------------------------------------------------------------
Fixed a SIGSEGV crash when a creature's ranged attack destroys another
creature that was already marked as the attacker for that turn.

Scenario: A hostile creature (e.g. squid) is adjacent to the player and
set as `attacker` in moveObjects(). Later in the same loop, a sea
serpent's specialAction() fires a ranged attack that hits the squid.
creatureRangeAttack() calls removeObject() which deletes the squid.
moveObjects() then returns a dangling pointer. gameCreatureAttack()
dereferences it → crash at game.cpp:3107.

Fix: After the moveObjects loop, verify the attacker pointer is still
present in the objects deque (via objectPresent()) before returning it.
If it was destroyed, return NULL.

Note: This is a latent bug also present in xu4.

File changed: src/map.cpp (Map::moveObjects)

2026-08-17: Tile transparency system
--------------------------------------
Implemented tile transparency matching xu4's "Transparency Hack"
setting. When enabled (Game Enhancements → Transparency Hack = On),
NPC/creature tiles overlay terrain with their black background cells
skipped, showing the terrain beneath.

Implementation uses a global flag (g_tileTransparent) checked in the
two low-level drawing functions (animDrawTile, animDrawTileScroll) and
the static tile path in drawTile(). No signature changes needed.

Transparency marker: space (0x20) + attr 0x00.
  - NPC/creature tiles (31-255) use space+0x00 for background cells
  - Terrain tiles (0-30) use full block (0xDB)+0x00 for solid black
  - Field tiles (68-71) use full block+0x00 (opaque, not transparent)

drawTile(vector) iterates all layers from back (terrain) to front
(creature), enabling transparency after the first layer. Matches xu4's
blending approach (xu4 uses alpha channel set by performTransparencyHack
at load time; tu4 checks character+attr at draw time).

Intro map: drawMapAnimated() draws terrain first, then NPC with
transparency via drawTileTransparent() wrapper.

Removed shadow size and shadow opacity settings (not applicable to
4×4 character tiles). Only the on/off toggle remains.
